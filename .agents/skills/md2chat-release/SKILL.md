# md2chat 发布

维护发布工具或规则按普通开发处理；用户要求准备新版本时才运行准备命令。发布命令是版本操作的唯一入口；具体参数与发布链路见 [README 发布步骤](../../../README.md#发布)，签名和真实升级验收见 [自动更新与签名发布](../../../docs/auto-update.md)。

## 准备版本

1. 根据用户指定版本与实际完成范围，准备详细说明正文（不带版本标题）和九语言摘要 JSON（不带版本号），各存到临时文件。遵循 [更新摘要规则](../../../docs/update-summaries.md)：用户摘要每版 1～3 条，必要提醒单列，技术细节归入详细说明；兼容性和验收范围沿用已验证事实。
2. 从仓库根目录运行：

   ```sh
   npm run release:prepare -- patch --notes-file PATH --summary-file SUMMARY_JSON_PATH
   ```

   将 `patch` 按发布范围替换为 `minor`、`major` 或明确的 `X.Y.Z`。命令校验 GitHub Latest、摘要九语言和历史完整性后，同步版本、详细说明，并在 `docs/releases/<主.次>/<版本>.json` 新增摘要文件，保留历史。正式发布时自动生成并验证历史索引、九语分片与校验值。校验失败时解决具体原因后重试；网络、鉴权或限流错误不视为首次发布。
3. 审阅版本与说明差异，运行 `npm run check`，再运行 `npm run release:verify -- --tag vX.Y.Z`。以命令全部通过和发布文件变更可审阅为准备完成条件。准备请求完成在此，保留变更供用户审阅。

## 正式发布

只有用户要求正式发布时，才创建并推送版本标签；普通「提交」或「推送 main」按代码提交处理，不自动升版或发版。

1. 对准备好的候选版本重新运行 `npm run release:verify -- --tag vX.Y.Z`。标签、package、lock 和更新说明首版本必须一致，说明必须有实质内容，候选稳定版本必须严格高于 GitHub Latest。Latest 不存在且由命令确认仓库可访问时，允许发布首个稳定版。
2. 使用明确文件列表提交并推送发布所需变更，再创建并推送同版本标签。不得用强制推送移动已发布的版本标签；失败后根据工作流实际状态修复或重试，先确认是否已有 Release。
3. 跟踪 `Desktop release`，直到安装包、自动更新清单、Release Latest 与同版本官网部署均成功，或明确报告失败环节。构建产物不等于正式发布；手动运行工作流只生成验证包。

main / PR 仅运行检查。正式标签先校验版本，再构建安装包与官网，检查完整发布资产后发布 Release 并设为 Latest，最后部署官网。签名与平台验收状态以实际证据为准。
