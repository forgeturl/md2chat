# 兼容性与证据范围

当前源码使用 Tauri 2。下文注明 Electron 的记录属于历史版本证据，目标客户端的粘贴和发送结果需在 Tauri 版重新验收。

## 2026-10-17 Tauri 迁移验证

- macOS 15.7.4 Intel 本机：27 项 Rust 单元测试、308 项 JavaScript 回归及 Clippy 静态检查通过。
- 显式原生剪贴板测试通过，确认纯文字、HTML、PNG、钉钉和飞书原生表示可写入并读回；测试恢复原剪贴板。这是系统传输证据，不是客户端粘贴证据。
- 直接运行通用包中的应用二进制，隐藏的真实 WKWebView 通过表格、代码、公式、Mermaid、后台转换保留编辑器内容，以及命令窗口隔离共 6 项检查。可用 `npm run desktop:test:render` 重跑渲染测试，虚构图片和报告写入 `release/qa/`。
- Mac 通用 DMG 为 14,939,583 字节，应用二进制含 `arm64` 与 `x86_64`；本次仅在 Intel Mac 运行。测试包使用本地临时签名，未公证，未正式发布。
- Windows 原生剪贴板核心的跨目标类型检查通过；完整 Tauri 构建被本机缺少 Windows SDK/CRT 阻塞，Windows 安装、运行和聊天客户端粘贴尚未验收。Apple Silicon 运行和所有 Tauri 客户端粘贴也需分别验收。

## 纯前端版本

| 能力 | 范围 |
| --- | --- |
| 解析、预览、表格转 PNG | 在浏览器内完成 |
| 本地图片 | 通过用户粘贴获得，浏览器内解码 |
| 远程图片 | 默认自动加载，依赖图片来源的 CORS 与访问权限 |
| 复制 | 默认标准 `text/html` 与 `text/plain`；企微有图时分段复制纯文字或独立 PNG，浏览器需允许剪贴板写入 |
| 聊天框图文混排 | 企微采用逐段粘贴，证据见下文；其他系统、浏览器和客户端需分别验证 |
| 排查 | 仅浏览器可见格式，不检查原生专有数据 |

建议在 HTTPS 或 localhost 页面使用。直接双击 file URL 可能遇到权限差异。无 Async Clipboard API 时，尝试浏览器原生 copy 事件；失败会明确提示，不会把静默丢图当成成功。

## 已知问题

- 一次 macOS 钉钉来源样本的浏览器粘贴事件提供了 `text/plain` 和 `text/html`；HTML 含远程图片引用，但没有独立图片数据，浏览器读取失败。没有据此确定是跨域、权限还是网络问题，也没有泛化到所有钉钉版本。样本正文、地址和截图未纳入仓库。
- 桌面版使用 macOS 原生剪贴板，网页仍使用浏览器 API；二者兼容性证据分别记录。
- 图片在网页中可见，不代表可以读取像素、写入剪贴板或被目标应用保留。每一环都需要独立验证。
- 公式与 Mermaid 转为 PNG；已在内置浏览器检查行内公式、分式、中文流程图与时序图的渲染。目标聊天框是否保留这些图片仍须实测。
- 表格单元格内公式暂保留源码；不支持 TeX 外部扩展、Mermaid 自定义配置和外部资源，含 HTML 标签的图形可能无法导出。
- 代码块转为 GitHub 浅色风格 PNG，保留语法高亮，去掉标题栏和行号；长行折行，长代码分图并标明页序。行内代码保留文字，代码图片不能在目标聊天框直接编辑，标准纯文本副本仍含完整源码。目标聊天框是否保留图片需实测。
- 本工具不提供自动消息发送，也不会调用聊天工具机器人 API。

报告问题时，请使用虚构的“文字 + 两张图片 + 表格”内容，分别记录来源、网页结果和目标粘贴结果。可以使用页面底部的元数据排查报告，避免提供完整工作消息。

## 剪贴板排查报告 v2

- 桌面「读取当前剪贴板」和浏览器读取／粘贴样本共用静态 HTML 扫描。报告显示图片 `src` 的类别（data、https、http、file、blob、cid、相对引用、空或其他），只记录查询参数与片段是否存在；内嵌图片额外显示 MIME、base64 标记及数据字节数。
- 每张图片显示数值尺寸属性、白名单属性名和附近最多四层标签，不显示属性值。未知属性、标签和系统格式名折叠为「other」或「其他格式」，不回显任意名称。图片和表格统计忽略注释及 script/style 等原始文本中的伪标签；词法结构不等同于浏览器最终 DOM 或客户端实际导入结构。
- Mac 钉钉专用格式的图片数与 HTML 图片数、独立图片格式数分开统计。Windows 显示「不适用（仅 macOS）」，不能据此推断 Windows 不支持图文。「最近复制目标」只记录本页操作，不代表当前剪贴板来源。
- 排查仅由点击或粘贴触发，不执行 HTML、不请求图片、不写回剪贴板、不上传或持久化正文。每次解析总量最多 8 MiB，最多检查 100 个格式、列出每份 HTML 的 20 张图片明细；超限或读取失败会明确提示。点击「复制排查报告」才会用报告替换当前剪贴板。
- 对比时先读取 md2chat 的转换结果，再读取从钉钉复制的同一条图文，最后一次性复制最近两份报告。中间截图或复制其他内容会替换剪贴板。报告可缩小 Windows 实现差异，不能单凭格式和标签计数认定客户端粘贴成功。

## Windows 钉钉兼容现状与验证

用户提供的 Windows 0.6.3 脱敏样本只有 `text/html`，包含两张 HTTPS 图片，图片位于 `article > p > img`；没有独立 PNG 或额外媒体属性。它证明钉钉复制出口能提供这类 HTML，不能证明粘贴入口接受任意 HTTPS 或本机文件图片。

v0.6.4 按上述结构改为仅 HTML、本机 PNG 文件引用。用户反馈钉钉粘贴完全空白；报告确认 HTML 含两张 `file` 图片。这否定了该次兼容尝试的可用性，但仍不能区分 HTML 入口被忽略、本机图片引用受限或其他客户端条件。

- 已恢复 HTML 与纯文本并存，避免 HTML 未导入时没有文字回退。纯文本中的 `[图片]` 仅是占位，不能算图片粘贴成功。Mac 钉钉仍保留原生私有格式。
- Windows 提供可选「钉钉分段复制（备用）」，分别写入可编辑纯文本和独立 PNG，按顺序粘贴。它不替代默认整段入口，不表示一次混排已修复，Windows 分段效果也需真机验证。
- 「剪贴板排查」增加无图 HTML-only 与当前 HTML 原样重写两个显式实验，缩小入口、传输封装、结构和图源之间的差异。重写保持读取到的 HTML 字符串，不承诺原生 CF_HTML 字节相同。不上传、存盘或请求 HTML 引用的图片。
- 原图已有合规 HTTPS 地址且能正常读取时仍保留原来源；表格、代码、公式和图表使用本机 PNG 缓存，没有自动上传或创建公网地址。Windows 下次成功复制钉钉内容后清理超过 7 天的旧图；编辑器/托盘只回读本应用缓存内内容校验通过的 PNG。
- Windows 打包流程已改为 Rust 原生剪贴板读写与 CF_HTML 字节校验；另有独立验证工作流和原生测试日志。它验证应用写入和系统读回，不代替钉钉粘贴验收。完整用例与人工结果模板见 [Windows 验证步骤](windows-clipboard-qa.md)。

历史 Electron 版的依赖源码：[Electron 44.8.0 ClipboardItem](https://github.com/electron/electron/blob/v44.8.0/shell/browser/api/electron_api_clipboard_item.cc#L493-L498) 将 HTML 交给 WriteHTML；其 Chromium 152.0.7977.167 在 [Windows 写入路径](https://github.com/chromium/chromium/blob/152.0.7977.167/ui/base/clipboard/clipboard_win.cc#L1050-L1058)调用 [HtmlToCFHtml](https://github.com/chromium/chromium/blob/152.0.7977.167/ui/base/clipboard/clipboard_util_win.cc#L1256-L1372)，自动生成头部、UTF-8 字节偏移与片段标记。当前 Tauri 版由 Rust 原生层生成 CF_HTML，并测试 UTF-8 字节偏移；不能把解码 HTML 中的 `StartFragment 无` 当成原生封装缺失的证据。

公开资料尚未找到可直接复用并确认解决 Windows 钉钉混排的实现。[Microsoft Clipboard 样例](https://github.com/microsoft/Windows-universal-samples/blob/main/Samples/Clipboard/cs/CopyText.xaml.cs)使用 HTML、纯文本及本地图片 ResourceMap；[Windows HTML Clipboard 规范](https://learn.microsoft.com/en-us/windows/win32/dataxchg/html-clipboard-format)定义通用片段格式，不能证明钉钉接受任意本机图片引用。

这是 v0.1 网页分段方案的历史测试；v0.2 网页默认标准图文，桌面版使用下述原生完整图文方案。这个结果只验证了当次 Chrome 与钉钉的输入框，不代表一次复制混排已修复，也不代表已验证消息发送或所有平台。测试草稿已清理。版本号未记录。

| 复制方式 | 当前企业微信的实际粘贴结果 |

据此，企微有图内容采用分段复制：网页和桌面分别写入一段纯文字或一张 PNG，用户按原文顺序依次粘贴。纯文字可直接复制，强调样式不保证保留。托盘企微图文转换打开独立分段面板，保留主编辑器输入，打开面板时不以整段混合格式覆盖剪贴板。

新版分段面板已完成实际端到端操作：

- 网页：原生 Chrome 中点击企微及各段复制按钮，依次粘贴 5 段“前文 → 表格 PNG → 中间文字 → 代码 PNG → 后文”，同一企微草稿完整保留顺序和两张图片。[输入框验证图](wecom-web-input.png)。
- 桌面：独立桌面实例中点击企微及各段复制按钮，依次粘贴 3 段“前文 → 表格 PNG → 后文”，同一草稿完整保留；直接键入并删除一个测试字符验证文字可编辑。[输入框验证图](wecom-desktop-input.png)。
- 分段面板为独立快照，不改原编辑器内容；每次只标记“已复制”，不会推断用户已粘贴或自动发送。
- 从企微自身复制图文时，若只得到图片文件引用、没有实际图片数据，托盘转换会提示重新复制，不会静默移除图片后输出纯文字。

Windows 企微、其他版本和消息发送后的最终效果均未验证，不能将 Mac 输入框结果泛化为全平台兼容。

## 2026-10-17 macOS 飞书一次混排实测

标准 HTML + 纯文本在当前飞书客户端中只保留文字和强调样式，两张内嵌 PNG 丢失。改为飞书原生编辑 fragment，加标准 HTML 与纯文本后，用户在展开的富文本输入框一次粘贴「前文 + 蓝图 + 中间文字 + 绿图 + 后文」，并提供发送后截图确认顺序、两张图片和粗体、斜体、删除线完整。

Mac 桌面版主窗口与托盘采用该格式，图片使用本机 PNG 缓存及新 UUID，不依赖账号配置。普通输入框可能丢图，必须先展开富文本输入框。此证据限本机客户端，网页和 Windows 飞书仍待验证；客户端产品版本号尚未从关于界面确认。详细用法、格式与自动传输测试见 [Mac 飞书适配](feishu-mac.md)。
